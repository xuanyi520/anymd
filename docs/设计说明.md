# anymd 设计说明

## 一、整体架构

```
                     ┌──────────────────────────────────┐
   命令行  ─────────→│                                  │
   拖拽    ─────────→│  cli.py  /  interactive.py       │
   MCP     ─────────→│  mcp_server.py                   │
                     └──────────────┬───────────────────┘
                                    │
                     ┌──────────────▼───────────────────┐
                     │           core.py                │
                     │  引擎调度 · 路径解析 · 元数据     │
                     │  批量并发 · manifest             │
                     └──────┬────────────────┬──────────┘
                            │                │
                 ┌──────────▼──────┐  ┌──────▼──────────┐
                 │  入向引擎        │  │  出向引擎        │
                 │  markitdown     │  │  pandoc         │
                 │  pymupdf4llm    │  │  Edge 打印      │
                 │  vision.py      │  │  Word COM       │
                 └─────────────────┘  │  openpyxl       │
                                      └─────────────────┘
```

三个入口共用同一个 `core.py`，所以命令行能做的 MCP 也能做，行为完全一致。

### 模块职责

| 文件 | 职责 | 行数量级 |
|---|---|---|
| `core.py` | 引擎调度、路径解析、frontmatter、批量、manifest | ~1000 |
| `cli.py` | argparse 定义、子命令分发、中文别名 | ~320 |
| `interactive.py` | 拖拽菜单、冲突处理、逐文件/批量流程 | ~450 |
| `vision.py` | OpenAI 兼容视觉接口、图片压缩、PDF 逐页 | ~400 |
| `mcp_server.py` | MCP 工具定义（4 个） | ~150 |

## 二、关键设计决策

### 2.1 为什么是两步转换，而不是直接 A → B

任意格式 → 任意格式没有通用通路。m 个输入格式 × n 个输出格式 = m×n 个转换器。

走 Markdown 中转变成 m + n 个。

**代价**：复杂版式（多栏、浮动图片、精确表格位置）必然损失。
**收益**：统一、可维护、任何新格式只要支持一个方向就能接上整个矩阵。

Markdown 只表达结构：标题、段落、列表、表格、代码、强调、链接、图片。**不表达**字号、颜色、分栏、浮动位置。这是刻意选择——AI 需要的是结构，不是样式。

### 2.2 引擎选择策略

PDF 是唯一有双引擎的格式：

```
engine == "auto" 且 后缀是 .pdf
    ↓
  用 pymupdf4llm
    ↓
  统计非空白字符数
    ├─ < 20           → 回退 markitdown
    ├─ < max(30, 页数×20) 且开了 vision → 逐页视觉识别
    └─ 否则            → 用 pymupdf4llm 的结果
```

为什么 PDF 特殊对待：pymupdf4llm 保留标题层级和表格，学术论文效果远好于 markitdown；但对扫描版完全无能，必须换路线。

其他格式 markitdown 已经够用，不设分支。

### 2.3 输出路径的三层防护

路径解析是最容易出错的地方，代码里有三道防线：

1. **输出 = 源文件**
   - `to_markdown`：自动改成 `<stem>.converted.md`
   - `from_markdown`：直接报错「输出路径不能与源文件相同」

2. **默认目录重名**
   - `_unique_output()` 自动加 `_1`、`_2`，最多试到 999

3. **显式指定输出**
   - 默认覆盖（符合"我要这个文件就在这"的直觉）
   - `--no-overwrite` 时跳过并记为失败

**为什么默认目录不覆盖、显式指定覆盖**：不指定输出 = 随手转一下，不该毁掉上次的结果；指定了输出 = 我明确知道要写这儿，覆盖是预期行为。

### 2.4 批量为什么用线程不用进程

PDF 转 md 的耗时大部分在 pymupdf（C 扩展，会释放 GIL），用 ThreadPoolExecutor 就能拿到接近线性的加速，同时避免了进程池在 Windows 上的 pickling 问题。

默认 4 线程：机械硬盘在 4 以上会 I/O 饱和反而变慢；SSD 可以调到 8。

### 2.5 MCP 的 batch_convert 为什么只返回摘要

128 个文件全返回，每个带 source/output/chars/error，JSON 轻松上 100KB，直接撑爆上下文窗口。

所以 MCP 版本的 batch 只返回：总数、成功数、失败数、**前 20 条**失败原因。完整数据在输出目录的 `manifest.json` 里，需要时再让 AI 去读。

### 2.6 frontmatter 的三个必要处理

```python
safe = (str(value).replace("\\", "/")      # ①
                .replace('"', "'")          # ②
                .replace("\n", " ")         # ③
                .replace("\r", " "))
```

① **反斜杠必须转成正斜杠**：YAML 双引号串里 `\P` 是非法转义，`E:\Paper` 会让解析器报错。
② **双引号换成单引号**：值里再有双引号会提前闭合字符串。
③ **换行压成空格**：多行值会破坏 YAML 结构。

## 三、五个必踩的坑

这些都是实际调试出来的，改代码前先看一遍。

### 坑 1：pymupdf4llm 的 OCR 探测会抛 UnicodeDecodeError

**现象**：转换任何 PDF 都在 reader 线程里抛 `UnicodeDecodeError: 'gbk' codec can't decode byte...`。

**原因**：pymupdf4llm 1.28 默认 `layout` 模式会执行 `tesseract --list-langs` 探测 OCR 能力。中文 Windows 下 tesseract 输出 GBK，在 UTF-8 模式取的 subprocess reader 线程解码失败。

**解决**：

```python
to_markdown(..., use_ocr=False)
os.environ.setdefault("TESSDATA_PREFIX", ...)
```

**教训**：调用第三方库时，它可能在你看不见的地方起子进程。

### 坑 2：YAML frontmatter 里的 Windows 路径

见 [2.6](#26-frontmatter-的三个必要处理)。生成时必须转成正斜杠。

### 坑 3：pandoc 会重复渲染 frontmatter 的 title

**现象**：生成的 Word/PDF 开头出现了两次标题。

**原因**：pandoc 读到 YAML 的 `title` 字段会自动渲染成文档标题，而 md 正文的第一个 `#` 也是一级标题。

**解决**：转换前生成临时 md，删掉 frontmatter 里的 `title` 行，再交给 pandoc。

```python
def _pandoc_input(src, text, ...):
    # 去掉 frontmatter 的 title 行，但保留其他元数据给 pandoc
```

### 坑 4：mcp 2.x 必须用 MCPServer

```python
# ✅ mcp >= 2.0
from mcp.server.mcpserver import MCPServer
mcp = MCPServer("anymd")

# ❌ 旧教程的写法，2.x 里已不可用
from mcp.server.fastmcp import FastMCP
```

另外：**`mcp.run()` 默认走 stdio，stdout 不能有任何杂输出**。任何一句调试 `print()` 都会让协议解析失败，表现为客户端提示 `CONNECTION_CLOSED`。调试信息一律写 `sys.stderr`。

### 坑 5：`.cmd` 里不能写中文注释

**现象**：双击批处理报 `'werShell' 不是内部或外部命令` 这种莫名其妙的错。

**原因**：cmd.exe 按 GBK 读取文件。UTF-8 编码的中文注释被按 GBK 解释后，可能解析出特殊字节（比如 `0x0A` 混进命令里），把一条注释拆成两行命令。

**解决**：`.cmd` 里只写 ASCII 注释（或者干脆不写）。需要区分终端编码时：

```bat
@echo off
setlocal
if defined MSYSTEM (
    set "PYTHONIOENCODING=utf-8"
) else (
    set "PYTHONIOENCODING=gbk"
)
"%~dp0.venv\Scripts\anymd.exe" %*
```

Git Bash 有 `MSYSTEM` 环境变量，走 UTF-8；PowerShell / CMD 没有，走 GBK。

## 四、视觉模型集成

### 4.1 接口约定

只依赖 OpenAI 兼容的 `/chat/completions` 形状：

```http
POST {VISION_BASE_URL}/chat/completions
{
  "model": "...",
  "messages": [{
    "role": "user",
    "content": [
      {"type": "text", "text": "<按 mode 生成的提示词>"},
      {"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}}
    ]
  }]
}
```

这样火山方舟、OpenAI、通义千问、智谱全部能接，只改两个环境变量。

### 4.2 三种触发路径

| 触发条件 | 走哪个函数 |
|---|---|
| 输入是图片文件 + `--vision` | `describe_image()` 单张描述 |
| PDF 抽出字符数低于阈值 + `--vision` | `pdf_pages_markdown()` 逐页渲染识别 |
| PDF/PPTX/DOCX 有内嵌图片 + `--vision` | `describe_images()` 抽图批量描述 |

### 4.3 成本控制

- 图片统一压到最长边 1800px（`_encode_image`）
- 内嵌图片最多 30 张（`MAX_IMAGES`）
- 扫描 PDF 默认最多 50 页（`--vision-max-pages`）
- 每页单独一次调用，失败不中断整体流程

## 五、如何扩展

### 加一个新的入向格式

1. 在 `core.py` 的 `render_markdown()` 里加分支
2. 如果 markitdown 已支持，不用改代码——`engine == auto` 会自动走 markitdown
3. 如果需要新库，改 `pyproject.toml` 的 `dependencies`

### 加一个新的出向格式

1. 在 `FORMAT_ALIASES` 加别名
2. 在 `PANDOC_OUT` 加映射（如果 pandoc 支持）
3. 在 `TARGET_EXT` 加扩展名
4. 如果 pandoc 不支持，在 `from_markdown()` 里加分支

### 加一个新的 MCP 工具

在 `mcp_server.py` 里加：

```python
@mcp.tool()
def my_tool(arg: str) -> str:
    """一句话说明。参数说明也写这里——AI 靠这个决定怎么调。"""
    return json.dumps({...}, ensure_ascii=False)
```

装饰器自动注册，不用改别的地方。

### 加一个新的视觉模式

在 `vision.py` 里找到提示词字典，加一个 key，然后 `cli.py` 的 `--vision-mode` choices 里同步加。

## 六、测试

`tests/make_samples.py` 生成各格式的测试样本：

```bash
.venv\Scripts\python.exe tests\make_samples.py
```

然后在 `tests\samples\` 里会得到 docx / pptx / xlsx / html / epub / pdf / csv 各一份。

回归测试：改动 `core.py` 之后，至少跑一遍双向转换：

```bash
anymd batch tests\samples --to md --outdir tests\out\md
anymd batch tests\out\md --to docx --outdir tests\out\docx
```

检查两次的 `manifest.json` 里 `failed` 都是 0。

## 七、已知技术债

| 问题 | 影响 | 想法 |
|---|---|---|
| `core.py` 近 1000 行，职责偏多 | 难维护 | 拆成 `io_paths.py` / `engines.py` / `batch.py` |
| 视觉模式提示词写死在 `vision.py` | 改提示词要读代码 | 抽成外部 yaml |
| 没有单元测试，只有手工回归 | 改动有回归风险 | 补 pytest，mock 掉外部引擎 |
| Edge 路径写死两个候选 | 装在别处就找不到 | 改成注册表查询 |
| `_extract_pipe_tables` 只认标准管道表 | 嵌套表格会丢 | 改用 markdown 解析库 |
| 没有进度条 | 批量转 1000 个文件时不知道到哪了 | 加 tqdm，或定期刷 manifest |
